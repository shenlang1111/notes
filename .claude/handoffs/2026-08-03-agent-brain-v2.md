## 2. 大脑方向（⚠️ 接替者必读，用户三次纠正后的最终版）

### 2.1 用户要什么 / 不要什么

| 用户要的 | 用户明确否决的 |

| 几个 AI **互通**，共享知识库当共同大脑 | "文档模拟的伪协作"（窗口不相通、靠改文档传话） |

| 大脑**学会更新迭代**（自动提炼 skill、越用越准） | 只会干固定活、不成长的系统 |
| 大脑**学会准确找到信息**（混合检索、带出处） | 死记硬背、翻不准、瞎编 |
| AI 之间**自己传消息**，省去用户人工传话 | 用户在中间当传话人 |
| 更好地**查找资料、更新想法** | "多一个帮你改东西的 AI" |

> **⚠️ 关键纠正（2026-08-03 用户原话）**：
> "你似乎有一个误解，就是你并不需要去改困难的任务，你需要做的是搭建一个大脑，然后这个大脑可以代替我的工作，不仅如此，他要学会更新迭代的能力，他要学会准确找到信息的能力。"
> "我觉得你想一次做好这个任务是非常困难的，我可以多开几个窗口并行这个任务。"
> **接替者必须内化**：你不是"认领难任务的执行者"，是"大脑的建造者"。注意力放在"大脑自身的能力"上，不是"任务板哪些难任务该我干"。

### 2.2 大脑的本质（四层能力架构）

```
┌─────────────────────────────────────────────────┐
│ 第4层 进化层 ｜ 自我更新迭代                       │
│   干完活 → 自动提炼经验 → 生成/更新 skill → 越用越准 │
├─────────────────────────────────────────────────┤
│ 第3层 记忆层 ｜ 跨会话不丢                         │
│   分层记忆：短期(本次)→中期(项目)→长期(事实/规则)   │
│   后台整合：定期把散经验合成结构化知识                │
├─────────────────────────────────────────────────┤
│ 第2层 检索层 ｜ 准确找到信息                       │
│   混合检索：语义(向量) + 关键词(BM25) 双轨           │
│   结果加权、去重、带来源                           │
├─────────────────────────────────────────────────┤
│ 第1层 接入层 ｜ 想法进得来、结果出得去               │
│   信箱/监听：任何 AI 或用户发布 → 触发               │
│   消息协议：谁发的/发给谁/内容/状态                 │
└─────────────────────────────────────────────────┘
```

> 完整版（各层验收标准）在 `.claude/handoffs/brain-blueprint-v1.md`。

### 2.3 实时互通的物理基础

- 用户确认：**移动端和桌面端共享同一个文件夹**，移动端可调动桌面端 → Trae 发布的内容**立刻落在本地文件**。
- 因此用 **fs.watch 事件监听**（文件一变，毫秒级触发），**不是**定时轮询。
- **⚠️ 前提待验证**：Trae 移动端是否真能写本地共享文件夹——建监听进程前先验证（让用户发一条，确认文件真的变了）。

### 2.4 技术要点（建大脑时必须处理）

1. **防死循环**：我干完活改文件也会触发监听 → 加"处理中标记"，让我改的不再触发自己。
2. **只做难的**：信箱里带"需要处理"标记的才动；简单问题/闲聊不碰（留给 Trae）。
3. **消息协议**：定义"一条消息长什么样"（谁发的/发给谁/内容/状态），所有 AI 统一用它写信箱。
4. **常驻进程**：电脑一直开（用户已确认），监听进程常驻后台当大脑中枢。

### 2.5 窗口分工模型（用户确认）

```
         你（临时传话人——大脑自动化前你先顶着）
            │ 开窗口 / 转达指令         │ 拿结果
            ▼                           ▲
     ┌──────────────┐           ┌────────────────┐
     │ 主大脑（我）   │ ←传指令── │ 技术验证员窗口   │
     │ 决策+验收+小活 │ ──拿结果→ │（试跑候选方案）  │
     └──────────────┘           └────────────────┘
```

- **为什么不用"多 Agent 并行改库"**（用户判断正确）：并行改的是**同一个库**，互相看不到 → 改重/冲突；跨页命名对齐有先后顺序，本质只能串行。
- **正确姿势**：改文件串行（主大脑把关），查资料并行（内部子代理），窗口分工拆任务。
- **当前窗口数**：2 个（主大脑 + 技术验证员）。数据来源补齐那批资料到位后，再开"内容修补员"。

### 2.6 双引擎分工（已确认，不废弃）

| 窗口 | 定位 | 负责 |
|---|---|---|
| **Trae（主窗口）** | 前台·主对话 | 日常对话/答疑/移动端记想法/处理任务 |
| **Claude Code（智能体 AI）** | 后台·大脑 + 执行引擎 | 建大脑中枢、实时监听、只接难任务、翻库/更新/批量 |

分工标准：会不会把主对话窗口撑脏——轻的/顺手/高频 = Trae；重的/批量/占上下文 = 大脑自动分给我。

### 2.7 三条底层原则（之前已确认，不废弃）

- **瘦上下文**：长期记忆存文件；窗口只放"身份+去哪查+本次任务"；干活开新上下文。
- **文件即记忆**：状态全落盘（ai-worklog/任务板/各页），上下文丢了可从文件恢复。
- **会话即进程**：一个大任务干完、结果落盘就开新会话，不硬撑。

## 9. 已知的坑（Gotchas）

- **部署超时/网络**：GitHub API 偶发 `fetch failed` → 重试可过；部署超时（360s 构建限制）大文件多时可能发生 → 文件已上传则等构建或补触发。
- **同一文件必须串行编辑**：并行会互相覆盖，导致内容丢失。
- **部署上传串行**：GitHub 并发写返回 409，重试可过（deploy.js 已处理）。
- **验证线上用 Node fetch**：PowerShell 的 Invoke-WebRequest 可能误报 404。
- **手机/微信缓存**：改版后加版本参数 `?v=` 强制刷新，或让用户 Ctrl+Shift+R。
- **Token 安全**：在 `.env`，不硬编码、不在对话里传。
- **SessionStart hook 生效**：中途配置不触发，需重开窗口或 `/hooks` 重载。
- **fs.watch 防循环**（建大脑时）：处理中标记避免自触发死循环。
- **GitHub 网页抓取被挡**：WebFetch 抓 github.com 返回"unable to verify domain safe"→ 用 WebSearch 结果 + 让验证员窗口本地 clone/试跑，不依赖网页抓取。
