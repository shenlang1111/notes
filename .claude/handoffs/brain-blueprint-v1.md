# AI 大脑蓝图 v1 — 天赐材料知识库

> 生成：2026-08-03 · 由主大脑（Claude Code）撰写
> **本文件是"AI 大脑"建设的唯一参照**：所有执行窗口对照此图干活，主大脑据此验收。蓝图是活的，随建设推进迭代。

---

## 0. 一句话目标

**建一个"大脑"代替用户当枢纽：用户把想法扔进知识库 → 大脑自动接、自动找信息、自动干难活、自动回写、自我迭代。** 用户不在中间传话。

## 1. 为什么是"大脑"而不是"任务分派器"

用户原话（2026-08-03 拍板）：
> "你并不需要去改困难的任务，你需要做的是搭建一个大脑，然后这个大脑可以代替我的工作，不仅如此，他要学会更新迭代的能力，他要学会准确找到信息的能力。"

关键区别——**不要做成**"多任务中转站"（一堆 AI 抢活、你当调度员）；**要做成**"代替用户的自主系统"（自己会找信息、自己会进化、自己把活干完回传）。

## 2. 大脑的四个能力层（从底层往上叠）

```
┌─────────────────────────────────────────────────┐
│ 第4层 进化层 ｜ 自我更新迭代                       │
│   干完活 → 自动提炼经验 → 生成/更新 skill → 越用越准 │
├─────────────────────────────────────────────────┤
│ 第3层 记忆层 ｜ 跨会话不丢                         │
│   分层记忆：短期(本次)→中期(项目)→长期(事实/规则)   │
│   后台整合：定期把散经验合成结构化知识                │
├─────────────────────────────────────────────────┤
│ 第2层 检索层 ｜ 准确找到信息                       │
│   混合检索：语义(向量) + 关键词(BM25) 双轨           │
│   结果加权、去重、带来源                           │
├─────────────────────────────────────────────────┤
│ 第1层 接入层 ｜ 想法进得来、结果出得去               │
│   信箱/监听：任何 AI 或用户发布 → 触发               │
│   消息协议：谁发的/发给谁/内容/状态                 │
└─────────────────────────────────────────────────┘
```

### 各层目标与验收标准

| 层 | 要建成的样子 | 验收标准（怎么算"成了"） |
|---|---|---|
| **接入层** | 文件监听 + 消息信箱 | 用户在 Trae 移动端发一条 → 文件一变 → 大脑感知到（秒级），不靠轮询 |
| **检索层** | 自动混合检索，替代手工 fanku | 问"TC-MAB 是什么"→ 秒回库内出处，不瞎编；命中率肉眼比 fanku 高 |
| **记忆层** | 跨会话分层记忆 | 上周纠正过"TC-MAB 是月桂酰"→ 这周再问不再犯；经验沉淀为可查文件 |
| **进化层** | 自动生成/更新 skill | 干完一类活 → 自动提炼成 skill → 下次同类活更快更准 |

## 4. 建设路线（分阶段，一个窗口一阶段，不贪多）

> 原则：**先跑通、再迭代**；每阶段都有可验收的产物；不依赖上一阶段完美再进下一阶段。

| 阶段 | 做什么 | 验收产物 | 依赖 |
|---|---|---|---|
| **0. 技术验证** | 拉候选方案试跑，看能不能接进文件库 | 《技术验证报告》——每方案打分 + 主/备选结论 | 无（可最先并行） |
| **1. 检索大脑** | 把 fanku 升级成自动化混合检索 | 检索能用：问即秒回库内出处 | 阶段 0 结论 |

| **3. 进化大脑** | 干完活自动提炼 skill | 自动生成新 skill / 更新机制 | 阶段 1+2 |
| **4. 接入大脑** | 文件监听 + 信箱 + 消息协议 | 移动端发 → 秒级感知 | 可与 1-3 并行 |

## 6. 窗口分工（怎么拆）

### 6.1 分工模型：主大脑统筹 + 执行窗口分干，用户临时传话

```
         你（临时传话人——大脑自动化前你先顶着）
            │ 开窗口 / 转达指令         │ 拿结果
            ▼                           ▲
     ┌──────────────┐           ┌────────────────┐
     │ 主大脑（我）   │ ←传指令── │ 技术验证员窗口   │
     │ 决策+验收+小活 │ ──拿结果→ │（试跑候选方案）  │
     └──────────────┘           └────────────────┘
```

### 6.2 为什么不用"多 Agent 并行改库"

| 并行类型 | 可行性 | 原因 |
|---|---|---|
| **并行查**（只读检索） | ✅ 可以 | 各查各的域，互不干扰，返回结论 |
| **并行改**（改同一库） | ❌ 不行 | 改的是同一批文件，互相看不到 → 改重/冲突；且跨页命名对齐有先后顺序，本质只能串行 |

结论：**改文件串行（主大脑把关），查资料并行（内部子代理）**。窗口分工解决"拆任务"，不靠 Agent 并行改同一库。

### 6.3 窗口拆法（当前阶段）

| 窗口 | 角色 | 干什么 | 提示词文件 |
|---|---|---|---|
| A | 主大脑（= 本窗口） | 决策+验收+清小活 | 已就位 |
| B | 技术验证员 | 阶段 0：试跑候选方案 | `.claude/handoffs/brain-window-verifier.md` |

> 后续阶段需要时再开：内容修补员（资料到位后）、检索实现员（阶段 1）、记忆实现员（阶段 2）——每个窗口一份提示词。

## 7. 约束与铁律（所有窗口必须遵守）

| 类别 | 规则 |
|---|---|
| **知识库铁律** | 改 HTML 必须同步改 MD（双格式成对）；部署用 `node tools/deploy.js --files <清单>`；部署必带 `--expect "文件:关键词"` 验证 |
| **留痕** | 干完活登记 ai-worklog（谁干了什么）；改库登记 CHANGELOG；新机制广播 mechanism-updates |
| **知识纪律** | 先翻库再开口；带出处不编造；翻不到明说"库里没有"；裸数据不当依据 |
| **职责边界** | 小改动自理；大改动（registry/nav/style/已有脚本/跨页批量/建页）登记任务板等主 AI 拍板 |
| **用户拍板权** | 所有关键决策（技术路线/架构/范围）用户拍板；执行窗口提供分析和材料 |
| **技术边界** | 阶段 0 只验证不接入；改现有库内容必须走铁律；自研脚本放 tools/ |
