## 一、部署经验

- **部署优先走 GitHub API 通道**：国内网络下 git push 不稳定（依赖加速器），api.github.com 直连稳定。上传用 Contents API，构建用 POST /pages/builds。国内镜像站（ghproxy）不支持 push，不适用。
- **一键部署脚本**：所有部署统一用 `node tools/deploy.js`——自动重新生成 mobile.html + 上传 + 触发构建 + 服务器端验证。不要手动逐个文件传。
- **上传必须串行**：并发写同一仓库会被 GitHub 返回 409 拒绝。教训：上传并发度 = 1。
- **部署后要服务器端验证**：不能只看"构建成功"，要拉取线上内容核对（footer 文案 0 次、面板数量、文件大小）。
- **验证本次修改内容**：部署后必须用 `--expect "文件:关键词"` 验证本次修改的标记上线，不能只做通用检查（用户曾因只做通用检查而质疑"没部署"）。
- **DoD 门禁**：任务宣布"完成"前必须逐项过 DoD（CHANGELOG/部署/验证），回复"完成"前展示自检清单——防止"写了规范不用"。

## 二、手机版经验

- **内容变更后必须重新生成 mobile.html**，否则手机版不同步（部署脚本已自动绑定生成）。
- **提取页面内容用配对计数**匹配 container 闭合标签，否则页面底部的 footer 会被截入每个面板（曾导致"参考资料反复跳"的 bug）。
- **面板用 div**（不用 section），避免与内容页的 section 标签冲突；内容页标签不平衡时用 cleanSections 兜底。
- **每次打开强制回首页**，忽略浏览器恢复的上次位置。

## 三、缓存经验

- **手机/微信浏览器缓存顽固**：改版后加版本参数（如 ?v=2）强制绕过缓存。
- **"看不到更新 ≠ 没部署"**：先排查缓存（清缓存/无痕/版本参数），再用服务器端内容核对是否真的更新了。

## 四、安全经验

- **Token 存本地 .env**（已 .gitignore），不在对话、脚本、仓库中传递。
- **Token 硬编码会被 GitHub 自动吊销**（Push Protection 拦截），泄露一次就要换新的。

## 五、内容维护经验

- **每条内容 HTML / MD 双格式同步维护**：HTML 用于网页展示，MD 用于 AI 检索。缺一个会报成对校验警告。
- **具体数据标注来源**：产品参数、市占率等标注"来源：产品手册/培训资料"；无法核实的数据明确说明，不冒充权威。
- **新增内容流程**：内容 → HTML → MD → registry.json → 重新生成 mobile.html → 部署。
- **分类意识**：日化知识之外的内容（AI 经验/日常）主动规划独立大类，不混入知识分类、不等用户指出。

## 八、文档管理与交接

- **4 个核心文档**：知识库维护规范（★★★ 必读，总规则）/ PROJECT_CONTEXT（★★ 必读，背景）/ CODE_WIKI（★ 推荐，技术）/ CHANGELOG（☆ 按需，追溯）。
- **阅读顺序**：规范 → 项目背景 → 技术维基 → 变更日志。新 AI 接手按此顺序读，最快进入状态。
- **交叉引用**：每个文档头部都有"文档关系"块，互相引用，打开任何一份都能看到全貌。
- **交接文档随项目更新**：PROJECT_CONTEXT / CODE_WIKI 必须反映当前状态（旧路径/旧机制会误导后续 AI，本次重写 v2.0 即是教训）。

## 六、多 Agent 协作经验

- **改动分级**：小改动（单页增补、单 MD 修改）各 agent 自理；大改动（分区、导航、UI 体系、脚本、批量改动）仅主 agent。
- **大改动配审核 agent**：独立复核产出（本轮审核发现 deploy.js 6 处问题，全部修复后才放心部署）。
- **改文件前先读最新版**，多会话同文件夹时防止互相覆盖。
- **GitHub 并发写保护**：同一时刻只允许一个部署流程，冲突（409）由主 agent 协调。
- **并行拆解**：任务按文件拆分给多个 agent 并行（各 agent 只碰分配的文件），关键产出配审核 agent 独立复核后才部署（本次 3 执行 + 1 审核并行实践成功）。
- **跨会话信息同步（唤醒识别）**：用户从其他对话框回来时说"你去看我们聊了什么"→ 第一时间按 LastWriteTime 扫描共享文件夹识别对方新写入的内容，不要直接说"我看不到"，别等用户第二次提醒。
- **并行分派是默认动作**：多步骤任务（≥3 个独立文件/步骤）默认拆给多个子代理并行执行（各自只碰分配的文件），执行前先声明拆分方案。
- **有建议即执行，别等逐条拍板**：给用户方案时，凡是已给出明确建议的部分直接落地；只有确实需要用户二选一的点才停下来问（2026-08-02 主 agent"方案列完等确认"被用户点名，教训）。
- **了解用户画像（闲聊 AI 沉淀 2026-08-03）**：闲聊中沉淀用户特质——务实有主见（给建议要带说服力理由、不空谈方案）、长线思维（关心"越用越值钱"的积累）、会用人（讨论找闲聊 AI、落地找主 agent、把关找审核 agent，各司其职）；用户认可与 AI 从"工具"变成了"伙伴"。下次怎么用：给建议带理由、把讨论和执行分清楚、信任比能力更难恢复。

## 七、与 AI 高效交流的技巧

1. **给上下文**：描述问题时说清"在哪（哪个页面/设备）、看到什么、期望什么"。例："手机上打开销售话术页，底部反复出现'天赐材料知识库持续更新中'"。
2. **说"要什么"**：直接说"把标题改为'与 AI 的交流经验'，内容要可复用的经验"比"这样不对"更高效——AI 才知道往哪改。
3. **大需求拆小步**：一次只确认一步（先看草稿→确认→再写入→再部署），避免返工。
4. **数据给来源**：涉及具体数字时说明出处（产品手册/培训材料），AI 总结更准、更敢用。
5. **先复述，再动手**：任务模糊或要讨论时，先一句话复述"我理解你要的是X"，确认后再做，避免理解错返工。
6. **讨论就只讨论**：用户说"讨论/完善"时，只给分析和材料，不推销方案、不催"要不要现在动手"，决定权在用户。

## 九、AI 智能体构想（2026-08-01 闲聊）

> 闲聊中讨论的构想：让现有知识库从"高级记录体"进化为"像你、比你懂得多"的个人 AI 智能体。

> **⚠️ 后续进展**：该构想已实际落地推进——2026-08-02 定"双引擎分工"（Trae 主对话 + Claude Code 执行）→ 2026-08-03 用户三次纠正后演进为 **"AI 大脑"方向**（代替用户当枢纽的自主系统，自我迭代 + 准确找信息），详见智能体设计存档与大脑蓝图（`.claude/handoffs/brain-blueprint-v1.md`）。下方选型表为 08-01 当时的讨论方案，其中 LLM 选型已被推翻。

### 现状认知

现有知识库本质是**仓库**——分门别类存放，需要时去翻。不会主动联想、不会追问、不会消化（只是存档，不是理解）。

### 理想形态

```
你的想法/资料 → 储存 → 检索 + 理解 → 输出像你的回答
```

- 储存：已解决（HTML + MD 双格式）
- 检索+理解：缺 RAG 层
- 像你的回答：缺人格化

### 安全顾虑

- 静态网站本身无攻击面（内容公开，无后端）
- 真正风险是 Token 泄露 → 已在防护（.env 不上传）
- 建议加一道：GitHub 两步验证（2FA）

### 推荐方案：自建 RAG 智能体

| 组件 | 选型 | 说明 |
|------|------|------|
| 聊天前端 | HTML + 原生 JS | 单页，类似现有 mobile.html 风格 |
| API 后端 | Python + FastAPI | 轻量异步框架 |
| 向量检索 | 读取 MD 文件 + Embedding API | 不依赖额外向量数据库 |
| LLM | ~~DeepSeek API~~ → **Claude Code** | 便宜，国内直连（2026-08-02 已推翻，改用 Claude Code） |
| 人格系统 | 一条 system prompt | 从知识库文本提炼说话风格 |

**核心流程：**
- 启动时：读取 `markdown/` 下所有 MD → 按段落切分 → 生成 Embedding 向量索引
- 每次对话：用户发消息 → 检索最相关 3-5 个片段 → 组装 prompt（片段 + 风格 + 对话历史）→ 调 LLM → 返回回答
- 每次结束：对话总结写回"会话记录"分区（HTML + MD 双格式）

**新增文件结构：**

```
ai-agent/
├── agent.py              # 主程序（FastAPI 服务）
├── kb_loader.py          # 读取 MD 知识库，生成索引
├── retriever.py          # 检索模块
├── chat.py               # 对话逻辑（组装 prompt + 调 LLM API）
├── config.py             # 配置
├── requirements.txt      # Python 依赖
├── personality.md        # 人格描述
├── templates/
│   └── index.html        # 聊天界面
└── .env                  # API Key（不上传）
```

## 十、思考收件箱设计讨论（2026-08-01）

### 背景

闲聊内容会越来越多、越来越杂，现有"会话记录"分区定位是"可复用经验"，不适合放半成品的想法。需要一个**临时暂存区**，先放、后续再统一整理。

### 定位

- **会话记录** = 成品仓库（已整理、可复用的经验）
- **思考收件箱** = 原料堆场（零散想法、未整理讨论，先放着后续再管）

### 设计要点

| 方面 | 建议 |
|------|------|
| 命名 | "思考收件箱"（与现有"笔记收件箱"呼应） |
| 结构 | 按日期/话题分独立页面，vs 一个大页面不断追加 → 建议按文件拆分，便于后续整理归档 |
| 域定位 | 新增 domain，独立于"会话记录" |
| 已有内容 | 第九节的"AI 智能体构想"是已整理的经验，留在会话记录合适 |

### 本次教训：部署必须紧跟文件创建

**问题：** 创建了新的会话记录文件（HTML+MD）后，没有立即执行部署，被用户指出"你已经读了规范，为什么不部署？"

**根因：**
- 误判了"部署"不属于"大改动"——文件创建是内容操作，部署是标准流程，不管大小改动都应该部署
- 把"registry.json 和 nav.js 是大改动"和"部署也是大改动"混为一谈

**教训：** 任何文件创建/修改，做完后**立即部署**，不因"大改动需主 agent 处理"而跳过部署步骤。部署是流程的终点，不是架构决定。`node tools/deploy.js --files` 可以只部署指定文件，不碰 registry/nav。**"大改动"限制的是架构变更，不是限制你上线内容。**

## 十一、Skill 安装与多 Agent 协作实践（2026-08-02）

> 用户想为 AI 智能体项目安装 Trae IDE 的 skill 扩展能力，通过多 Agent 并行安装 + 审核 Agent 复核，一次性完成 16 个 skill 的安装与质量验证。

### 背景

在讨论 AI 智能体方案时，用户发现 Trae IDE 有 skill 扩展机制（类似插件），可以让 AI 具备更多能力（如 PDF 处理、记忆管理、自主运行等）。用户希望把这些 skill 装好，辅助后续的 AI 智能体开发。

### 安装流程

```
用户要求装 skill → 调查 skill marketplace → 按类型分 3 组 → 3 个 Agent 并行安装 → 审核 Agent 复核 → 汇报结果
```

### 安装的 Skill 清单

16 个 skill 清单与调用方式见 SKILL_GUIDE.md（2026-08-02 安装快照，权威清单以 SKILL_GUIDE 为准）

### 经验总结

1. **多 Agent 并行安装效率高**：3 个 Agent 各装一组，互不冲突，安装 + 审核共 16 个 skill 一次性完成。
2. **审核 Agent 不可或缺**：虽然本次 16 个 skill 全部安装正确，但审核机制确保了不会因为安装错误影响后续开发。
3. **Skill 体系是 AI 智能体的基础能力**：`unified-memory` + `ck` 解决记忆问题，`autonomous-agent-harness` 提供自主运行框架，`dispatching-parallel-agents` 实现多 Agent 协作，`session-handoff` 保障上下文不丢失——这些 skill 联合构成了 AI 智能体的核心底座。
4. **记录本次经验**：Skill 安装流程（调查 → 分组 → 并行安装 → 审核 → 汇报）可作为后续安装其他 skill 的标准化流程。

## 十二、2026-08-03 闲聊记录（D 盘首日，规范五-1 自动提炼实践）
